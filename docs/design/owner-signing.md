# Owner-signed envelopes and client-minted API keys

Status: implemented in `packages/crypto` (this PR). Server and enclave
changes are listed under [Migration](#migration) and land in their own PRs.

## Problem

Envelope v1 as first specified bound `{secret_id, owner_id, policy}` into the
AES-GCM AAD with an unkeyed SHA-256. That detects *edits* to a stored
envelope, but not *substitution*: the KMS public key is public, so anyone who
can write to the database (the hosted operator, or an attacker with a dump
and write access) could seal their own credential under a victim's
`secret_id` and `owner_id`, with a policy of their choosing. The victim's
agent would then use the attacker's credential.

Independently, the server minted `cpk_` API keys and stored their hash. A
database writer could insert a key hash of their own and the enclave would
accept the key, because the enclave's only authorization check was "does the
server say this key may use this secret".

Both problems have the same root cause: the enclave had no way to tell which
objects the *owner* produced. This design gives it one.

## Threat model delta

Before: the server is untrusted for confidentiality only. It cannot read
plaintext, but it can decide which ciphertext an agent gets and which keys
are authorized.

After: the server is untrusted for confidentiality *and* integrity of secrets
and authorization. A database writer can no longer:

- substitute a different envelope under a victim's ids;
- change any field of a stored envelope, including `kms_key_version`;
- authorize an API key, widen what a key may use, or mint a key at all.

A database writer can still:

- deny service (delete or withhold envelopes and grants);
- serve *older* owner-signed objects, bounded as described under
  [Freshness](#freshness-rollback-and-revocation);
- read cleartext policies and metadata (names, ids, fingerprints).

The owner's device joins the TCB: it holds the owner signing key, as it
already held the plaintext at sealing time.

The enclave's clock is part of the freshness argument. The VM operator can
set the guest clock, so `now` must not come from the VM clock alone; see
[Freshness](#freshness-rollback-and-revocation) for the rule.

## Design

One Ed25519 *owner key* per user, generated by the CLI and never sent to the
server. Every object the enclave acts on chains to it:

```
API key  cpk_<fp>_<random>          fp = fingerprint(owner_pk)
   │
   ▼  lookup_hash ──▶ server ──▶ grant (owner-signed: key_bind, secrets, exp)
   │
   └──▶ enclave: fingerprint(grant.owner_pk) == fp
                 verify(grant.sig, owner_pk)
                 grant.key_bind == bind_hash(api_key)
                 envelope.owner_pk == grant.owner_pk
                 verify(envelope.sig, owner_pk)
                 envelope.version >= grant.secrets[secret_id]
                 ... only then KMS unwrap and AES-GCM open
```

The agent's API key is the root of the chain on the enclave side. It names
the owner fingerprint, so the enclave learns which public key everything
must chain to from the *agent*, not from the store. The store can only serve
objects that owner actually signed.

## Formats

All hashes are SHA-256. `tagged_sha256(tag, data) = sha256(tag || 0x0A ||
data)`. `canonical_json` is defined in
`packages/crypto/src/carapace_crypto/canonical.py` (sorted keys, no
whitespace, no floats, integers within ±2^53-1, depth ≤ 32). All binary
fields inside signed objects are standard padded base64 (RFC 4648 §4), and
parsers reject non-canonical encodings and duplicate JSON keys.

### Owner key

- Ed25519. 32-byte seed, 32-byte public key `owner_pk`.
- Every `owner_pk` is checked with `validate_public_key` wherever it is
  parsed, fingerprinted or verified against: small-order points and
  non-canonical encodings (`y >= p`) are rejected. OpenSSL accepts a
  small-order public key, and for one of those `R = identity, S = 0`
  verifies over any message, so a grant or envelope naming such a key could
  be "signed" by anyone. Generated keys never hit the check. The server must
  run it when registering an owner key (calling `fingerprint` does).
- `fingerprint = tagged_sha256("carapace-owner-fp-v1", owner_pk)[:16]`.
- Signing input for every object: `context || 0x0A || canonical_json(body)`.
  `context` never contains a newline; canonical JSON escapes newlines, so the
  split point is unambiguous.

### API key

```
cpk_<fingerprint: 32 lowercase hex>_<random: 64 lowercase hex>    (101 chars)
lookup_hash = tagged_sha256("carapace-key-lookup-v1", key_ascii)   # server stores
bind_hash   = tagged_sha256("carapace-key-bind-v1",   key_ascii)   # grant binds
```

The server indexes keys by `lookup_hash`; the grant it stores carries
`bind_hash`. So a database dump holds both hashes, but neither yields the
other or the raw key: the random part is 256 bits from a CSPRNG, and the
enclave recomputes both hashes from the raw key the agent presents. The
server therefore cannot produce a key string that any grant names. The two
tags keep the index value from doubling as the value a signature binds.

### Envelope v1 (amended)

```
header  = {"v": 1, "secret_id", "owner_id", "owner_pk", "version", "policy"}
aad     = sha256(canonical_json(header))
dek     = random(32)
nonce   = random(12)
ct      = AES-256-GCM(dek, nonce, plaintext, aad)          # ct || 16-byte tag
wrapped = RSA-OAEP(SHA-256, MGF1-SHA-256)(kms_public_key, dek)
body    = header + {"kms_key_version", "wrapped", "nonce", "ct"}
sig     = Ed25519(owner_seed, "carapace-envelope-v1" || 0x0A || canonical_json(body))
stored  = body + {"sig"}
```

- `owner_pk`: base64 of the raw 32-byte public key.
- `version`: positive integer chosen by the owner, strictly increasing per
  secret. The CLI uses Unix seconds at sealing time.
- `owner_pk` and `version` are inside the AAD as well as the signature, so
  even an attacker holding the owner seed cannot re-label an existing
  ciphertext to another key or version; they would have to re-seal, which
  requires the plaintext.
- `canonical_json(header)` is capped at 64 KiB. The check runs on the
  canonical bytes, and canonicalization itself bounds nesting depth (32), so
  a header that cannot be canonicalized is rejected before anything else
  touches the policy.
- `secret_id` is a random UUID (v4) generated by the CLI and never reused,
  including after deletion; a fresh id is what makes "retire and re-create"
  meaningful, because no existing grant can name it.
- `owner_id` is the server-side account the secret belongs to. It is signed
  so the server cannot re-home an envelope, but the enclave does not check
  it: the enclave binds to `owner_pk`, which is what the API key names.

### Grant v1

```
body = {"v": 1,
        "owner_pk": base64(owner_pk),
        "key_bind": base64(bind_hash),
        "secrets":  {"<secret_id>": <min envelope version>, ...},   # ≤ 100 entries
        "iat": <unix seconds>,
        "exp": <unix seconds>}                                      # iat < exp ≤ iat + 90 d
sig  = Ed25519(owner_seed, "carapace-grant-v1" || 0x0A || canonical_json(body))
wire = body + {"sig"}
```

- `secrets` maps each secret the key may use to the lowest envelope version
  the enclave may accept for it. An empty map is a *tombstone*.
- Default TTL 30 days, hard cap 90 days (rejected at parse time).
- `verify_grant` accepts `iat - 300 s ≤ now < exp`.

## Enclave verification algorithm

Inputs: the raw API key presented by the agent, the requested `secret_id`,
the server client, the KMS unwrapper, a per-boot `MonotonicCache`, and
`now` (see the clock rule under Freshness).

```
1.  key   = ApiKey.parse(raw)                       # ApiKeyError → 401
2.  resp  = server.post("/internal/keys/verify",
                        {"key_hash": hex(key.lookup_hash), "secret_id": secret_id})
          # 404 → 403 (unknown key). An honest server returns the key's
          # *current* grant even when it is revoked (tombstone), narrowed
          # or does not cover secret_id; scope is decided in step 6.
3.  wire  = load_json_object(resp.body)             # duplicate keys → 502
    grant = Grant.from_dict(wire["grant"])          # GrantError → 403
4.  verify_grant(grant, key, now=now)               # key mismatch, signature,
                                                    # expiry → 403
5.  cache.observe(key.fingerprint, "grant", key.lookup_hash, grant.iat)
                                                    # StaleError → 403
6.  floor = grant.min_version_for(secret_id)        # GrantScopeError → 403
7.  env   = Envelope.from_json(server.get(f"/internal/secrets/{secret_id}"))
                                                    # EnvelopeError → 502
8.  require env.owner_pk == grant.owner_pk          # → 502
    verify_envelope_signature(env)                  # → 502
    cache.observe(key.fingerprint, "envelope", secret_id, env.version)
                                                    # StaleError → 502
9.  plaintext, policy = open_with_dek_unwrapper(
        env, kms_unwrap,
        expected_secret_id = secret_id,
        expected_owner_pk  = grant.owner_pk,
        min_version        = floor)
          # signature / stale / decryption errors → 502; KMS is reached only
          # after the signature and version checks pass
10. enforce policy, execute, receipt includes
    fingerprint(grant.owner_pk), env.version and grant.iat
```

Step 5 runs after step 4 so an unverified grant can never poison the cache,
and before step 6 so a tombstone (which has no secrets and fails step 6)
still advances the cache: once a running enclave has seen the tombstone,
the server cannot revive the older grant for the rest of that boot. This
only works if the server *serves* the tombstone: `/internal/keys/verify`
must return the current grant for every known key, tombstones included, and
must not pre-filter by `secret_id`. A server that answered 404 for
tombstoned or out-of-scope keys would keep every tombstone and narrowed
grant away from the cache. The one key it answers 404 for is one revoked
*without* a tombstone (the web UI path): its stored grant is still the last
live one, which the enclave would honour until `exp`, so an honest server
withholds it and the enclave refuses the key as unknown.

Step 8 records the envelope version once the owner signature has verified
and before KMS is called, so a rolled-back envelope costs no unwrap. The
signature is checked again inside step 9; that costs one Ed25519
verification.

`open_with_dek_unwrapper` checks, in order: `v == 1`, `secret_id`,
`owner_pk` (constant-time), signature, `version >= min_version`, then
unwraps and decrypts. The first four are cheap and offline; KMS is never
called for an envelope that is not the expected owner's.

Errors distinguish only "your key" (4xx) from "the store" (5xx). Messages
never include envelope or grant contents.

## Freshness, rollback and revocation

The enclave has no persistent state across boots (Confidential Space, no
sealed storage in v0.1) and no trusted clock other than the VM's. A
malicious server can therefore always serve the *last object the owner
signed* rather than the *current* one. The design bounds how long that
works and lets the owner choose the bound.

Three mechanisms:

1. **Grant expiry.** A grant is valid for at most 90 days (default 30). A
   revoked key, a narrowed grant, or a raised version floor that the server
   withholds takes effect no later than the old grant's `exp`. The CLI can
   renew grants automatically while the owner key is available; short TTLs
   are the owner's knob for tighter revocation.
2. **Per-secret version floors.** When the owner re-seals a secret with
   version `N` (rotation), the CLI reissues grants for every key that uses it
   with floor `N`. Once an agent's grant carries the new floor, the server can
   no longer serve the old envelope to it. Rollback is possible only for
   agents still holding an older grant, and only until that grant expires.
3. **Per-boot monotonic cache.** Within a boot the enclave records the
   highest `grant.iat` per key and the highest `envelope.version` per secret
   it has *verified*, and refuses anything lower. Once a running enclave has
   seen a newer grant or envelope, the server cannot roll it back for the
   life of that boot. Entries are partitioned by owner fingerprint (the one
   the object verified against), with an LRU bound per owner (1 000) and on
   the number of owners (10 000). Traffic under one owner key can neither
   evict another owner's entries nor plant a value under another owner's
   `secret_id`. Traffic under 10 000 *distinct* owner keys between two of a
   victim's requests can still flush the victim's partition, and owner keys
   are free to generate: the server can do it, and so can any tenant unless
   the server caps owner keys per account and the enclave rate-limits
   requests per fingerprint. This mechanism is therefore best-effort within
   a boot; the guarantee comes from 1 and 2. `observe` holds a lock, so the
   cache can be shared by handlers running on a thread pool.

Grant issuance keeps `iat` strictly increasing per key even within one
second: `create_grant(..., previous_iat=...)` bumps the new `iat` above the
grant it replaces, so a create-then-revoke or renew-then-narrow in the same
second still reads as newer to the cache.

**Clock.** The VM operator controls the guest clock, so an enclave that
trusted it alone could be held at a time when an expired grant was valid.
The enclave takes `now = max(vm_clock, iat of its latest attestation
token)`, refreshes the token at boot and at least every hour, and never lets
`now` decrease within a boot. The attestation token is issued by Google's
attestation service against a trusted clock, so the operator cannot turn
the enclave's view of time back. The operator *can* hold it still by
blocking token refresh and slowing the guest's timers, but not for long:
the token also gates KMS (workload identity federation checks its expiry
against Google's clock), so an enclave that cannot refresh loses KMS access
once its token and federated credentials expire, about an hour later, and
serves nothing new. The bound on the delay therefore comes from KMS, not
from the refresh schedule, and holds only as long as the enclave never
caches DEKs or plaintext beyond the 60 s below. This is listed in the threat
model as the residual clock dependency.

Revocation semantics, from the owner's point of view:

| Action | Honest server | Malicious server |
|---|---|---|
| Revoke key (`revoked_at` + tombstone grant) | Next fetch (≤ 60 s) | Old grant works until `exp` |
| Narrow a grant (fewer secrets) | Next fetch (≤ 60 s) | Old grant works until `exp` |
| Rotate secret in place (re-seal, raise floors) | Next fetch (≤ 60 s) | Old *and new* value until each old grant's `exp` |
| Retire `secret_id`, re-create under a new id | Next fetch (≤ 60 s) | New value never; old value until the old grant's `exp` |
| Rotate the credential at its provider | Immediate | Immediate |

"Next fetch" is bounded by the enclave's 60 s object cache (below). Two
consequences for the malicious-server column:

- Rotating a secret *in place* does not cut off a revoked key. Floors are
  minimums, so a withheld tombstone plus the new envelope (version `N ≥`
  the old floor) hands the new value to the revoked key. To keep a new
  value away from a revoked key, seal it under a fresh `secret_id` and
  reissue grants only for the keys that should keep access. `carapace key
  revoke --hard` should do exactly that.
- Nothing in this design takes the *old* value away from a revoked key
  before the old grant's `exp`, because a database writer can keep serving
  the old envelope and old grant. The only hard cutoff is to rotate the
  credential at its provider so the old value stops working. The CLI should
  say so on every revoke.

What is *not* provided: a bound tighter than `exp` against a malicious
server without owner action, and detection of a withheld object (the enclave
cannot know a newer grant exists). A signed transparency log of owner
actions, checked by the CLI against the enclave's receipts, closes that gap
and is deferred to a later version.

## Owner key lifecycle

**Storage.** The CLI generates the key at `carapace init`, stores the seed
in the OS keychain when available and otherwise in
`~/.config/carapace/owner.key` with mode 0600, and registers the public key
with the server (`POST /v1/owner-keys`). The server keeps one or more public
keys per user so the UI can show fingerprints and reject envelopes signed by
unknown keys; it never sees a seed.

**Adding an API key or renewing a grant** never requires re-entering a
secret. Both are grant operations.

**Rotating an API key** is: mint a new key, issue its grant, revoke the old
one. No re-sealing.

**Rotating the owner key** requires re-sealing every secret, because
`owner_pk` is inside each envelope's AAD and the plaintext exists only on
the owner's device at sealing time (and inside the enclave). This is rare
and deliberate: an owner key that could be swapped without the plaintext
would be a key the server could swap. A later version can add an
enclave-mediated re-seal (owner signs a request under the old key; the
enclave decrypts and re-seals under the new `owner_pk`), which keeps the
plaintext inside the TCB.

**Loss.** Existing agents keep working until their grants expire. The owner
cannot issue new grants, so recovery is: generate a new key, register it,
re-enter and re-seal each secret, mint new API keys (the fingerprint is part
of the key string) and update agents. The CLI should print a recovery
phrase at `init`; BIP39 encoding of the seed is planned but not required for
v0.1.

**Compromise.** An attacker with the seed can sign envelopes and grants. On
its own that lets them do nothing the server could not already do to
*their own* account; combined with database write access it lets them
substitute secrets and authorize keys for the victim, which is the pre-design
attack. Because the owner never holds plaintext after sealing, a seed leak
does not reveal stored secrets. Recovery: revoke all keys, delete all
secrets, generate a new owner key, re-seal. The server should let a user
mark an owner key `retired` and refuse new envelopes and grants under it;
existing ones are covered by grant expiry.

## Web UI in v0.1

The web UI cannot hold the owner key without either sending it to the
server (which defeats the design) or keeping a second, browser-resident key
(which requires re-sealing every secret to add it). For v0.1 the web UI is
therefore **read-only for secrets and grants**: list secrets and their
fingerprints, view receipts, and revoke keys through the server
(`revoked_at`), which an honest server enforces immediately and a malicious
one within `exp`. Sealing, minting and granting happen in the CLI.

A browser-resident WebCrypto key (non-extractable, IndexedDB) as a second
owner key is the intended v0.2 path.

## Domain separation and canonical encoding

Every signature and hash carries a distinct context string:

| Use | Context / tag |
|---|---|
| Envelope signature | `carapace-envelope-v1` |
| Grant signature | `carapace-grant-v1` |
| Owner fingerprint | `carapace-owner-fp-v1` |
| API key lookup hash | `carapace-key-lookup-v1` |
| API key bind hash | `carapace-key-bind-v1` |

A signature produced under one context never verifies under another, so a
stored grant cannot be replayed as an envelope signature or vice versa, and
the server cannot derive `bind_hash` from `lookup_hash`. Test vectors cover
both cross-context cases.

The signed body of each object is exactly its stored JSON minus `sig`, run
through `canonical_json`. There is no separate "signing form": what the
store holds is what was signed, byte for byte after canonicalization, and
the enclave's parser rejects every *value* with two encodings (non-canonical
base64, duplicate keys, floats, unsafe integers). The JSON text around the
values is still malleable: whitespace, key order, string escapes and `-0`
all parse to the same object and so verify. Nothing may hash or compare
the stored JSON text; derive identities from parsed fields or from `sig`.

## Format versioning

Envelope v1 is amended in place rather than bumped to v2. No v1 envelope
exists outside this repository's test vectors: PR #6 (the store) is not
merged and nothing is deployed. A v2 label would commit the enclave to
accepting v1 forever or force a migration for zero users. The `v` field
remains the escape hatch for real changes later. Grant and API key formats
are new and start at v1.

`packages/crypto/tests/vectors/envelope_v1.json` and `grant_v1.json` are
the normative vectors, regenerated by `tests/vectors/generate.py`.

### Enclave broker PR (after #5)

Implement the algorithm above with `ApiKey.parse`, `load_json_object`,
`Grant.from_dict`, `verify_grant`, `Envelope.from_json`,
`open_with_dek_unwrapper` and `MonotonicCache`. The KMS unwrapper validates
`kms_key_version` against the configured key ring before building a
resource name.

- Cache verified grants and envelopes in memory for at most 60 s to avoid
  one server round trip per request; the monotonic cache still applies on
  refresh. This is the "next fetch" latency in the revocation table.
- Cache unwrapped DEKs keyed by `(owner_pk, secret_id, version, sig)` for
  the same 60 s, so repeated requests for one envelope cost one KMS call.
  The key includes `sig`, so a different envelope can never hit.
- Rate-limit KMS unwraps per owner fingerprint (the fingerprint is known
  from the API key before any server call). Any tenant, or a server
  replaying valid objects, can otherwise run up KMS usage; the limit turns
  that into a per-tenant denial of service rather than a shared bill.
- Derive `now` as described under Freshness (attestation token `iat`,
  monotonic within the boot).

### CLI

`carapace init` (owner key, register public key), `carapace secret put`
(seal with `version = now`), `carapace key create` (mint key, issue grant,
register lookup hash), `carapace key renew`, `carapace key revoke
[--hard]`.

## Guarantees

With an honest enclave image and Cloud KMS as specified in
`docs/ARCHITECTURE.md`, and the owner's device uncompromised:

- An agent presenting key `K` can only ever decrypt envelopes signed by the
  owner key whose fingerprint `K` names, under a grant that owner signed for
  `K`, covering that `secret_id`, at or above the version the owner pinned.
- Nobody without the owner seed can produce such an envelope or grant. The
  server, a database dump and a database writer are all "nobody".
- A database writer's remaining powers are denial of service and replay of
  older owner-signed objects, the latter bounded by grant expiry (≤ 90 days,
  owner-chosen), by version floors, and best-effort within a boot by the
  per-owner monotonic cache.
